# 1. Agent Output Contract

[← Index](./README.md) · Next: [CLI Design →](./02-cli-design.md)

---

Every CLI command writes exactly one JSON object to stdout and exits. No extra text, no stderr mixing, no human formatting. Agents parse one line and move on.

## Wire envelope (CLI ↔ Proxy ↔ Extension)

Every message that crosses a boundary uses the same JSON envelope. The shape is shared by the HTTP body the CLI POSTs, the WS frame the proxy forwards to the extension, and the WS reply the extension sends back. Keeping one envelope (instead of one per hop) means the proxy stays a dumb relay and any field can be matched on either side.

```json
// Request
{
  "protocol_version": 1,
  "id": "01HZX9C2K8R7Q3VG9MNPYJVZ4D",
  "action": "click",
  "params": { "selector": "#submit" },
  "session": "default",
  "deadline": 1714000030000,
  "destructive": true
}

// Response
{
  "protocol_version": 1,
  "id": "01HZX9C2K8R7Q3VG9MNPYJVZ4D",
  "ok": true,
  "data": { "clicked": true },
  "page": { ... },
  "replay": false
}
```

| Field              | Type    | Required | Purpose                                                                                                                       |
|--------------------|---------|----------|-------------------------------------------------------------------------------------------------------------------------------|
| `protocol_version` | int     | yes      | Currently `1`. CLI/proxy/extension all reject mismatched versions with `PROTOCOL_VERSION_MISMATCH`. Bumped on breaking changes.|
| `id`               | string  | yes      | The **idempotency key**. ULID or UUIDv4. Generated by the CLI, threaded through unchanged. See [Idempotency](#idempotency-key-and-replay).|
| `action`           | string  | yes      | One of the supported actions.                                                                                                 |
| `params`           | object  | yes      | Action-specific parameters.                                                                                                   |
| `session`          | string  | yes      | Routing field. The session name owns a sticky tab pin in the extension; two agents driving the same browser pass different names so their pins do not collide. Default `"default"`. Validated as `[a-z0-9_-]{1,32}`. Full semantics in [08-tab-management.md → Sticky pin per session](./08-tab-management.md#sticky-pin-per-session). |
| `deadline`         | int     | yes      | Absolute epoch-ms after which the request is dead. The CLI computes it from its own timeout; proxy and extension both honor it.|
| `destructive`      | bool    | yes      | Set by the CLI from a static per-action table (see [Per-action idempotency policy](#per-action-idempotency-policy)). The extension's dedupe layer keys off this. The field is sent on the wire (not derived) so a single source of truth is auditable in `/log`. |
| `ok`               | bool    | response | Single branch point for the agent.                                                                                            |
| `replay`           | bool    | response | `true` if this response was served from the extension's dedupe cache (i.e. the action did not run a second time). Logged but not surfaced to the agent in normal CLI output; available via `/log`. |

The CLI generates `id` once per invocation. **The same `id` must be used for every retry of the same logical operation** — that is what makes retry safe for destructive actions. If the agent re-runs `bproxy click "#submit"` from scratch, the CLI generates a fresh `id` and the extension treats it as a new operation; this is the agent's intent.

### Frame routing

DOM-touching actions accept an optional `frame` field in `params` that scopes the action to a single iframe inside the active tab. Three forms are supported, mirroring Playwright's `frameLocator` / `page.frame({ url })` ([Playwright — Frames](https://playwright.dev/docs/frames)):

```jsonc
"params": { "selector": "#pay", "frame": { "selector": "iframe[name^='__privateStripeFrame']" } }
"params": { "selector": "#pay", "frame": { "index": 1 } }                 // depth-first across all frames
"params": { "selector": "#pay", "frame": { "url": "/stripe\\.com/" } }    // string substring or /regex/
```

Omitted `frame` → top frame (`frameId === 0`). The CLI translates `--frame <ref>` to one of the three sub-fields based on its shape. The extension's resolver and edge cases are in [04-extension.md → Frame routing](./04-extension.md#frame-routing-and-frame-detection); the resulting `frameId` is **not** echoed back in the response envelope to keep it small — agents that need the round-trip can include the `frame` reference in the `data` block themselves on a per-action basis.

## Idempotency key and replay

The protocol guarantees, per (id, action, params) tuple:

- **Idempotent (read-only) actions** — `text`, `screenshot`, `images`, `elements`, `outline`, `dom`, `wait`, `tabs`, `tab`, `status`: at-least-once. Replays may re-execute. The agent sees consistent results because the action has no side effects on the page.
- **Destructive actions** — `click`, `type`, `navigate`, `eval`: at-most-once for a given `id`. The extension's dedupe table (see [04-extension.md → Dedupe table](./04-extension.md#dedupe-table-and-request-lifecycle)) returns the cached response on a re-delivery instead of re-running the action.

"Exactly-once" is not offered. The literature is consistent on this — message systems pick at-most-once or at-least-once and let the application pick per operation. We follow the same pattern as Stripe's idempotency keys (server caches the result of the first request under the key and replays it on subsequent retries; see [Stripe — Designing robust and predictable APIs with idempotency](https://stripe.com/blog/idempotency)) and the Phoenix Channels reconnect-and-rejoin convention where the application is responsible for tracking what it has already seen ([Phoenix — Channels guide](https://hexdocs.pm/phoenix/channels.html)). AWS API Gateway / Lambda Powertools and Square use the same shape: client-supplied key, server-side cached result, time-windowed expiry ([AWS — Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)).

Residual: if an `eval` script has its own external side effects (POSTs to a third-party API, mutates `localStorage` on a remote service through a fetch), the dedupe table only protects the *invocation* — not those side effects. The agent must treat `eval` with external effects the same way it would treat any user-written shell script: idempotent by construction or not at all.

## Per-action idempotency policy

| Action       | Destructive? | Replay semantics    | Notes                                                                |
|--------------|--------------|---------------------|----------------------------------------------------------------------|
| `text`       | no           | at-least-once       | Pure read.                                                           |
| `screenshot` | no           | at-least-once       | Pure read. Re-capture is fine. Subject to the visibility check in [08-tab-management.md → Screenshot capture](./08-tab-management.md#screenshot-capture); a re-delivery on a now-non-visible tab returns `TAB_NOT_VISIBLE` rather than a cached image. |
| `images`     | no           | at-least-once       | Pure read.                                                           |
| `elements`   | no           | at-least-once       | Pure read.                                                           |
| `outline`    | no           | at-least-once       | Pure read.                                                           |
| `dom`        | no           | at-least-once       | Pure read.                                                           |
| `wait`       | no           | at-least-once       | Idempotent by design — re-waits if necessary.                        |
| `tab list`/`status` | no    | at-least-once       | Read-only metadata.                                                  |
| `tab pin`/`tab unpin`/`tab open`/`tab close` | yes | at-most-once per id | Mutate the session's pin and/or open/close a Chrome tab. Dedupe table returns cached result on re-delivery. |
| `click`      | yes          | at-most-once per id | Dedupe table returns cached result on re-delivery.                   |
| `type`       | yes          | at-most-once per id | Same.                                                                |
| `navigate`   | yes          | at-most-once per id | Same. A re-delivery during navigation returns the cached terminal state.|
| `eval`       | yes          | at-most-once per id | Same. Side effects of the script itself are the agent's concern.     |

The CLI sets the `destructive` flag from this table. Adding a new action requires adding a row here and to the matching switch in the CLI.

## Success shape

```json
{
  "ok": true,
  "data": { ... }
}
```

`data` varies per action. Fields are kept minimal — no filler, no echo of the request.

Every response from a content-script action includes a `page` context block (see below).

## Error shape

Every error response uses a single structured envelope. The envelope is normative: the CLI, proxy, and extension all emit it; agents branch on `error.code` and `error.retry` without parsing free text.

```json
{
  "ok": false,
  "error": {
    "code": "SELECTOR_NOT_FOUND",
    "category": "target",
    "retry": false,
    "suggestedAction": "fix the selector or wait for the element",
    "message": "No element matches '#submit-btn'",
    "details": { "selector": "#submit-btn", "matchCount": 0 }
  }
}
```

| Field                     | Type                              | Required | Purpose |
|---------------------------|-----------------------------------|----------|---------|
| `ok`                      | bool                              | yes      | Single branch point for the agent. Always `false` in the error envelope. |
| `error.code`              | string                            | yes      | Machine-readable code from the [canonical table](./06-failure-modes.md#canonical-error-code-table). |
| `error.category`          | string                            | yes      | One of `connection`, `auth`, `protocol`, `target`, `timing`, `policy`, `internal`. |
| `error.retry`             | `true` \| `false` \| `"conditional"` | yes      | Retry guidance. `conditional` means "retry iff `suggestedAction`'s precondition is met"; see [06-failure-modes.md → `retry: conditional` semantics](./06-failure-modes.md#retry-conditional-semantics). |
| `error.retryAfterMs`      | int                               | optional | Deterministic floor (ms) before a retry could succeed. Modelled on Stripe's `Stripe-Should-Retry` plus exponential-backoff guidance ([Stripe — Idempotent requests](https://docs.stripe.com/api/idempotent_requests)). Absent when no useful floor is known. |
| `error.suggestedAction`   | string                            | yes      | One short phrase the agent can act on. Not a paragraph. |
| `error.message`           | string                            | yes      | One-line human/agent explanation. Free text. |
| `error.details`           | object                            | optional | Per-code structured payload; shape documented in [06-failure-modes.md](./06-failure-modes.md). Agents that don't recognise a `details` field MUST ignore it (per RFC 9457, [Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457.html)). |

The `error` object is shaped to be drop-in compatible with RFC 9457 / 7807 problem-details: `code` plays the role of `type`, `message` the role of `detail`, and `category` is a bproxy-specific extension that the agent uses for first-pass branching. The full taxonomy and the `details` schema per code live in [06-failure-modes.md](./06-failure-modes.md). This page documents only the envelope.

### `details` shape per code (summary)

The `details` object is free-form per code; the canonical schema is in [06-failure-modes.md](./06-failure-modes.md). The most common shapes:

| `error.code`              | `details` shape |
|---------------------------|-----------------|
| `AUTH_REQUIRED`           | `{ "reason": "missing_token" \| "bad_token" \| "host_mismatch" }` |
| `PROTOCOL_VERSION_MISMATCH` | `{ "expected": int, "got": int, "side": "cli" \| "proxy" \| "extension" }` |
| `SELECTOR_NOT_FOUND`      | `{ "selector": string, "matchCount": 0 }` |
| `SELECTOR_AMBIGUOUS`      | `{ "selector": string, "matchCount": int }` |
| `WAIT_TIMEOUT`            | `{ "check": string, "elapsedMs": int }` |
| `NEVER_SETTLED`           | `{ "busiestRoots": [{ "selector": string, "mutationsPerSec": number }] }` |
| `NAVIGATED_DURING_ACTION` | `{ "fromUrl": string, "toUrl": string }` |
| `FRAME_DETACHED`          | `{ "frameId": int, "parentUrl": string }` |
| `RESTRICTED_URL`          | `{ "url": string, "reason": "scheme_chrome" \| "scheme_chrome_extension" \| "scheme_view_source" \| "host_chrome_web_store" \| "scheme_file_no_optin" \| "scheme_about_no_optin" }` |
| `TAB_CLOSED`              | `{ "session": string, "tabId": int, "lastUrl": string, "closedAt": int, "reason": "user_closed" \| "page_closed" \| "command_closed" \| "window_closed" }` |
| `NO_TAB_TARGETED`         | `{ "session": string, "reason": "unpinned" \| "session_cleared" \| "first_command_failed_to_resolve" }` |
| `TAB_NOT_VISIBLE`         | `{ "session": string, "tabId": int, "windowId": int, "reason": "not_active" \| "minimized" \| "no_window", "currentlyActiveTabId": int? }` |
| `EVAL_ERROR`              | `{ "error": string, "stack": string }` |
| `INTERNAL_ERROR`          | `{ "where": string }` |

Codes not listed above either carry no `details` or use a shape unique to one code (documented inline in [06-failure-modes.md](./06-failure-modes.md)).

## Page context on every response

Every command that touches the page (`click`, `type`, `text`, `elements`, `images`, `outline`, `dom`, `eval`, `wait`) appends a `page` block to the response:

```json
{
  "ok": true,
  "data": { "text": "..." },
  "page": {
    "url": "https://app.example.com/dashboard",
    "title": "Dashboard",
    "state": "ready",
    "busy": false
  }
}
```

| Field   | Type   | Values / Meaning                                                                                              |
|---------|--------|---------------------------------------------------------------------------------------------------------------|
| `url`   | string | Current `location.href`. Updated synchronously on `pushState`/`replaceState`/`popstate`/`hashchange` via the history patch (see [Page State → SPA navigation detection](./05-page-state.md#spa-navigation-detection)) so it is truthful even on the response to the click that triggered the SPA route change. |
| `title` | string | Current `document.title`.                                                                                     |
| `state` | string | **Advisory.** `"loading"` · `"settling"` · `"ready"`. See [Page State Detection](./05-page-state.md) for the (adaptive) detection logic. |
| `busy`  | bool   | **Advisory.** `true` if loading indicators detected (spinners, skeletons, `aria-busy`).                       |

This block is cheap (4 fields, ~100 tokens) and gives the agent situational awareness on every call.

`state` and `busy` are **advisory hints**, not a contract the agent should branch on. Destructive actions (`click`, `type`, `navigate`) auto-wait on their own target's actionability — they do not consult `state`. Read-only actions (`text`, `outline`, …) return the page as it is at the moment of the call. The hint is useful for two things:

- The agent can log it for human inspection.
- The agent can pick a `bproxy wait` strategy from it (e.g. `state: "settling"` + `busy: true` → likely worth a `wait selector` against the new content rather than another speculative read).

The previous design exposed `state` as a primary contract; this is corrected to match the model used by Playwright (auto-wait on actions, explicit waiters for cross-cutting conditions). See [Page State → Page-state field is advisory](./05-page-state.md#page-state-field-is-advisory) for the detail.

## Token budget

Agent output is consumed by LLMs. Every extra token costs money and context window.

Rules:
- No redundant fields. Don't echo the command back.
- `text` action: return `{ "ok": true, "data": { "text": "..." } }` — not wrapped in metadata the agent didn't ask for.
- `screenshot` action: return `{ "ok": true, "data": { "image": "<base64>" } }` — just the payload.
- `elements` action: flat list, numbered, one line per element. No nesting, no full attribute dumps.
- Text content is truncated at 10,000 chars with a `"truncated": true` flag. The agent can use `eval` for full extraction if needed.

## Error codes

The canonical vocabulary lives in [06-failure-modes.md → Canonical error code table](./06-failure-modes.md#canonical-error-code-table). Every code there is a valid value of `error.code`; nothing else is. The seven categories are documented in [06-failure-modes.md → Categories](./06-failure-modes.md#categories), the disambiguation rules in [§ Taxonomy rules](./06-failure-modes.md#taxonomy-rules), and the deprecation list in [§ Deprecated codes](./06-failure-modes.md#deprecated-codes).

Agents typically branch in two steps:

1. On `error.category` for the gross shape (e.g. `connection` → tell the user; `target` → fix the selector; `timing` → maybe wait and retry).
2. On `error.code` for the specific recovery, using `error.suggestedAction` as the one-line hint and `error.details` for any structured payload.

Three values of `error.retry`:

- `true` — transient; retry verbatim. If `error.retryAfterMs` is set, wait at least that long.
- `false` — the agent must change something before retrying.
- `"conditional"` — retry iff the precondition in `error.suggestedAction` is satisfied (e.g. for `NAVIGATED_DURING_ACTION`, retry iff the new URL is the page the agent intended). See [06-failure-modes.md → `retry: conditional` semantics](./06-failure-modes.md#retry-conditional-semantics).

Example:

```json
{
  "ok": false,
  "error": {
    "code": "NO_CONNECTION",
    "category": "connection",
    "retry": true,
    "retryAfterMs": 30000,
    "suggestedAction": "open the browser and reload the extension",
    "message": "No browser extension connected"
  }
}
```

## Exit codes

- `0` — success (`ok: true`)
- `1` — command error (`ok: false`, infrastructure or action failure)
- `2` — CLI usage error (wrong args, printed before any JSON)

Exit code `2` is the only case where output is not JSON — it prints a usage line to stderr. This only happens if the agent calls `bproxy` with malformed syntax.
