## Task 3: Update `docs/solution/extension.md`

**Files:**
- Edit: `docs/solution/extension.md`

**Purpose:** Heaviest edit surface. Align the extension spec with the rethought architecture: popup-driven pairing, dual-world content script model, shadow-DOM aware discovery, tiered write strategy.

**What changes:**

§ "Project Layout":
- Add popup entrypoint (`entrypoints/popup/` or `entrypoints/popup.html` + `entrypoints/popup/main.ts` per WXT convention).
- Add `utils/discovery.ts` (or similar) for shadow-DOM aware element resolution.

§ "WXT Configuration":
- Popup entrypoint will be auto-discovered by WXT. Note it in manifest overrides if action config is needed.

§ "Background Service Worker":
- Responsibility #2: replace "listens for `chrome.runtime.onMessageExternal` from CLI helper" with "listens for internal message from popup on pairing completion."
- SW lifecycle: replace `pair.bootstrap` external message handling with internal `pair.complete` message from popup.

§ "Content Script":
- Current spec: isolated world only (`world: 'ISOLATED'`).
- Add: MAIN-world execution via `chrome.scripting.executeScript({ world: 'MAIN' })` for actions that need page-owned runtime handles. This is not a second content script — it is on-demand script injection from the background SW when a write action targets a hostile editor.
- Document the decision boundary: reads and standard form fills stay isolated; runtime-API writes enter MAIN world for the specific call, then exit.

§ "Action Handlers > Write actions":
- `fill`: add tiered strategy. (1) Standard inputs: paste-flavored events from isolated world (existing spec). (2) Hostile editors: detect editor runtime handle (Quill `__quill`, Lexical `__lexicalEditor`, etc.) via MAIN-world probe; mutate via editor's own API. (3) `auto` method tries paste first, falls back to runtime-API on failure.
- Note: runtime-handle detection is a specialized pass scoped to the active editor root, not a full-page scan.

§ "Pairing (No Options Page)":
- Full rewrite. Replace external-messaging contract with popup-driven claim:
  - Popup UI: input field for pairing code + claim button.
  - Popup calls `POST /pair/claim` directly (localhost fetch, daemon token not required — popup uses the pairing code as the auth factor).
  - On success: popup stores `extensionToken` + `wsUrl` in `chrome.storage.local`, sends internal message `{ type: 'pair.complete' }` to background SW.
  - Background SW reads stored token, reconnects WS.
- Remove: `sender.id` validation, `expiresAt`/`nonce` checks on external message (these belonged to the dead Plan A flow). The daemon's `/pair/claim` route handles code validation; the popup is a thin UI.

New section — "Shadow-DOM Discovery":
- Document the strategy: element resolution must check `element.shadowRoot` and descend into open shadow roots.
- Progressive approach: start with fast probes (active element, visible dialogs in light DOM), then shadow-root traversal scoped to the action's intent.
- Note: closed shadow roots are not pierceable; this is accepted. The extension handles open shadow roots, which cover the validated case (LinkedIn's `#interop-outlet`).
